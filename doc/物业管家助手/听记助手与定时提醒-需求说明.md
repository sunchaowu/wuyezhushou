## 1. 背景与目标

管家在楼栋现场沟通时，常边聊边记：收费情况、报修诉求等。现有操作依赖手动点选，效率低且易漏记。

本需求新增能力如下：

1. **听记助手 — 收费记录**：从口语中识别与物业费收缴相关的事实，提案写入房屋缴费信息。  
2. **听记助手 — 事件记录**：从口语中识别报修/故障等业务事件，写入事件（或等价记录）。  
3. **听记助手 — 沟通界面联动**：沟通中提到具体房屋（如「一单元 201」）时，自动切换并打开该房沟通记录界面。  
4. **听记助手 — 特征标签**：识别内置/自定义标签并提案挂到房间；自定义标签支持**描述性介绍**以提升语义匹配。  
5. **定时提醒**：对未完成事项（如待跟进收费、待处理事件）按设定时间在本机提醒。

**非目标（明确不做）：**

- 不与语音助手「对话闲聊」、不语音播报回复（必要时仅 UI 疑问 + 选项）。  
- 不联网调用云端 ASR / 大模型 / 推送服务。  
- 不在后台（App 未处于约定场景）长期偷听（首期范围见下）。

## 3. 需求一：听记助手 — 收费记录

### 3.1 需求概述

在楼栋网格听记模式下，从连续语音中识别**收费相关**业务事实，关联到具体房屋，提案修改缴费状态/月数（及必要时备注），经确认后写入本机数据库。

### 3.2 用户场景

| 场景 | 示例口述 | 期望 |
|------|----------|------|
| 明确欠费 | 「601 欠费三个月」 | 提案：601 → 欠费 3 个月 |
| 无硬关键字但仍是收费 | 「602 刚收到 100 元」 | 判定需记录；因系统以「月」计量，通常弹选项（换算/记备注/忽略） |
| 疑问 + 否定答复 | 「听说 602 的 100 元收到了吗？」「没收到」 | 前半句建「待核实」不直接写已收；否定答复后提案「未收到/维持欠费」等 |
| 无关闲聊 | 「中午吃啥」 | 忽略 |

### 3.3 功能需求

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F-PAY-01 | 网格页进入开启听记、离开停止；页面内可持续收音（配合 VAD，无人说话时低功耗） | P0 |
| F-PAY-02 | 本机 ASR 将语音转为文本（中文为主） | P0 |
| F-PAY-03 | 抽取收费相关槽位：房号、收缴动作族（收/交/缴/付/到账/欠…）、月数、金额（元）、语气（断言/疑问/传闻） | P0 |
| F-PAY-04 | 「要不要记」判定：房号（或当前选中房上下文）+ 收费事件信号 → 进入提案；否则忽略 | P0 |
| F-PAY-05 | 疑问/传闻不直接落库，进入「待核实」短时状态；绑定后续短答复（收到了/没收到） | P0 |
| F-PAY-06 | 提案以确认卡片展示；用户确认后调用现有缴费更新逻辑写入 SQLite | P0 |
| F-PAY-07 | 金额（元）与「月」计量不一致时，**禁止静默换算**；必须选项：记备注/原声、按规则换算（若已配置月单价）、忽略等 | P0 |
| F-PAY-08 | 支持映射到现有 `PaymentType`（欠费/预存/正常）及月数字段 | P0 |
| F-PAY-09 | 可选：将 ASR 原文摘要写入该房业主原声/沟通记录作为附证 | P1 |

### 3.4 业务规则

1. 默认关联：有明确房号用房号；无房号但有「这户/这一家」且存在当前选中房时可用当前房；否则弹选房或忽略。  
2. 待核实超时（建议 15–30 秒，可配置）未得到有效答复 → 作废，不写入。  
3. 否定答复优先于传闻命题中的「已收到」表述。  
4. 写入失败须提示原因，不得部分静默失败。

### 3.5 验收要点

- 给定用例集中，收费相关句能提案；无关句不弹窗、不写库。  
- 「收到了吗？ / 没收到」不会误记为已收款。  
- 「602 刚收到 100 元」不会在未确认情况下改月数。  
- 飞行模式/断网下功能完整可用。

## 4. 需求二：听记助手 — 事件记录

### 4.1 需求概述

在同一听记模式下，识别**非收费类**业务事件（首期以报修/工程维修为主），关联房屋并创建本机事件记录，供后续跟进与提醒。

### 4.2 用户场景

| 场景 | 示例口述 | 期望 |
|------|----------|------|
| 报修 | 「602 刚刚说家里漏水，需要工程上面维修」 | 创建事件：房 602，类型=维修报修，摘要含漏水/需工程维修 |
| 仅现象 | 「603 电梯老出问题」 | 可提案为事件或要求补全类型（选项） |
| 与收费同场 | 先聊缴费再聊漏水 | 分别产生收费提案与事件提案，互不覆盖 |

### 4.3 功能需求

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F-EVT-01 | 与收费共用听记开关与 ASR 管道；通过意图分流到「事件」 | P0 |
| F-EVT-02 | 抽取事件槽位：房号、现象（漏水/停电/门坏…）、诉求（维修/报修/派人…）、来源（业主说/转述） | P0 |
| F-EVT-03 | 命中「房号 + 故障/报修信号」判定需要记录事件 | P0 |
| F-EVT-04 | **本机持久化事件实体**（见数据要求），含状态：待处理 / 处理中 / 已完成 / 已取消 | P0 |
| F-EVT-05 | 创建前展示确认卡片；歧义时给选项（记事件 / 只记原声 / 忽略） | P0 |
| F-EVT-06 | 事件列表：按楼栋/状态筛选；可从房间进入查看该房事件 | P0 |
| F-EVT-07 | 支持手动创建/编辑/完结事件（不依赖语音） | P0 |
| F-EVT-08 | 事件类型首期至少包含：维修报修；预留投诉、催办、其他 | P1 |
| F-EVT-09 | 弱降级：若事件模块未就绪，允许临时写入「业主原声+报修标签」（仅过渡，正式版须真事件） | P2 |

### 4.4 事件数据（逻辑字段）

| 字段 | 说明 |
|------|------|
| id | 本机主键 |
| buildingId / roomId | 关联楼栋与房屋 |
| type | 维修报修 / 投诉 / 其他… |
| title/summary | 短摘要（可由槽位生成） |
| rawText | ASR 或手工原文（可选） |
| status | 待处理 / 处理中 / 已完成 / 已取消 |
| source | 听记 / 手工 |
| createdAt / updatedAt / completedAt | 本机时间戳 |
| reminderAt | 可选，关联提醒 |

### 4.5 验收要点

- 「602…漏水…工程维修」可确认后生成一条待处理事件。  
- 事件可在断网环境下创建、查询、改状态。  
- 与收费听记互不误伤：缴费句不建成维修事件，报修句不改缴费月数（除非同句多意图且分别确认）。

## 5. 需求三：听记助手 — 特征标签（含描述字段）

### 5.1 需求概述

听记过程中识别与房间特征标签相关的表述，提案为当前/指定房屋**添加或移除**标签（确认后写入）。  
当标签**短名称无法被口语直接命中**时，允许在定义标签时填写**描述性介绍**，供本机语义匹配使用，提高自定义标签命中率。

### 5.2 用户场景

| 场景 | 说明 |
|------|------|
| 名称直接命中 | 标签名「宠物」，口述「602 有宠物」→ 提案添加 |
| 名称难命中、靠描述 | 标签名「保姆住」，描述「家里请了住家保姆或护工长期居住」；口述「请了个保姆住这儿」→ 可凭描述语义匹配到该标签并提案 |
| 多标签 | 「又有老人又有车」→ 提案多个标签供确认勾选 |
| 无房上下文 | 仅闲聊提到标签相关词 → 不挂到错误房间 |

### 5.3 功能需求

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F-TAG-01 | 听记可匹配本机全部特征标签（内置 + 自定义） | P0 |
| F-TAG-02 | 特征标签增加字段 **`description`（描述性介绍）**，创建/编辑标签时可填写；用于听记语义匹配，界面可展示 | P0 |
| F-TAG-03 | 匹配优先级：标签名精确/包含 → 别名（若有）→ **描述文本关键词/语义相似度** → 内置同义族 | P0 |
| F-TAG-04 | 描述可为空；为空时仅靠名称（及别名/内置同义）匹配 | P0 |
| F-TAG-05 | 命中后出确认卡片（添加/移除），确认后写入房间特征关联 | P0 |
| F-TAG-06 | 设置页文案提示：名称宜短；若口语说法与名称不一致，请填写描述以便语音识别 | P0 |
| F-TAG-07 | 描述与名称均参与本机匹配，**不上传、不联网解释** | P0 |
| F-TAG-08 | 可选：别名列表（短词），与描述互补；描述偏整句说明，别名偏关键词 | P1 |

### 5.4 数据字段

在现有 `feature_tags` 上扩展：

| 字段 | 说明 |
|------|------|
| description | TEXT，可空；描述性介绍，供听记语义匹配与设置页展示 |
| aliases | 可选（P1）；JSON/子表，短别名列表 |

### 5.5 验收要点

- 仅名称能命中的标签，行为与预期一致。  
- 名称不易上口、但描述写清口语场景的自定义标签，在对应口述下能进入提案（经确认后写入）。  
- 描述留空不影响原有按名称使用。  
- 全程离线。

## 6. 需求四：听记助手 — 沟通界面联动（自动切房）

### 6.1 需求概述

管家在楼栋网格听记模式下与业主/同事沟通时，一旦口语中明确提到本楼栋内某套房屋（如「一单元 201」），系统应**自动将界面切换到该房屋，并打开沟通记录页**，展示该房全部历史沟通内容，便于边聊边对照、继续记录。

可与收费提案、事件提案并行：先切房看沟通记录，再对收费/事件做确认写入。

### 6.2 用户场景

| 场景 | 示例口述 | 期望 |
|------|----------|------|
| 房号 + 业务词 | 「一单元 201，现在楼上很吵」 | **满足「房号+业务词」** → 自动打开 **1 单元 201** 沟通记录页；可同时提案事件「噪音扰民」等（写入仍走确认卡片） |
| 房号 + 收费业务 | 「602 欠费两个月」 | 切到 602 沟通页 + 收费提案 |
| 房号 + 报修业务 | 「603 漏水要工程修」 | 切到 603 沟通页 + 事件提案 |
| 仅点名房屋（无业务词） | 「我们看下 602」 | **不自动跳转**（避免闲聊点名误切界面） |
| 房号歧义 + 业务词 | 「201 很吵」且多单元均有 201 | 不盲目跳转；弹选项选单元/房，或忽略 |
| 非本楼栋房号 | 提到本楼不存在的房号 + 业务词 | 不跳转；可轻提示「本楼未找到」或忽略 |
| 短时间重复同一房 | 连续多次「201 很吵」 | 已在该房沟通页则不重复闪烁跳转 |

### 6.3 功能需求

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F-NAV-01 | 从口语中解析房屋定位信息：单元（如「一单元」「1 单元」）、房号（如 201、602）；支持与本楼栋房间主数据匹配 | P0 |
| F-NAV-02 | **触发条件（已确认）**：须同时具备「可解析房号」与「业务词/业务意图」才自动切房；**仅提房号不跳转** | P0 |
| F-NAV-02a | 在 F-NAV-02 满足且房屋唯一匹配时：**立刻自动导航**打开该房**沟通记录界面**，展示该房全部沟通记录；**不**展示跳转前确认条/可撤销倒计时 | P0 |
| F-NAV-03 | 打开沟通页后，听记上下文「当前房」切换为该房，后续「这户」类指代默认指向此房 | P0 |
| F-NAV-04 | 匹配 0 套：不跳转；可选非打断式提示「未找到该房」 | P0 |
| F-NAV-05 | 匹配多套：弹出选择列表（单元+房号），用户点选后再打开；超时未选则取消本次导航 | P0 |
| F-NAV-06 | 防抖：同一 `roomId` 在冷却时间内（建议 8–15 秒，可配置）不重复自动打开 | P0 |
| F-NAV-07 | 用户正在编辑输入框/确认卡片交互时，延迟跳转或待交互结束后再跳，避免打断输入 | P1 |
| F-NAV-08 | 跳转过程完全离线，仅查本机房间与沟通数据 | P0 |
| F-NAV-09 | 切房时若同句含事件/收费信号，导航与提案可同时发生：先/并行打开沟通页，提案卡片叠在上层或返回网格后再确认（实现可选，须在设计中统一） | P0 |
| F-NAV-10 | 支持关闭「自动切房」（听记仍可记收费/事件）；默认开启 | P1 |

### 6.4 业务规则

1. **定位范围**：仅限**当前听记所在楼栋**内的房屋；不跨楼栋自动跳转（跨栋为后期）。  
2. **单元解析**：口语「一单元 / 1 单元 / 一单」等映射到本楼栋单元编号规则（与建房时单元/房号规则一致；若房间号本身已含单元信息则按现有 `roomNumber` 匹配策略执行）。  
3. **打开目标**：默认进入现有「房间沟通记录」页（与双击进沟通一致的数据源），用户可看到全部历史沟通。  
4. **自动跳转 vs 写入**：切房导航属于「界面联动」，**不视为**已确认写入收费/事件；写入仍须确认卡片（除非另有高置信静默策略且评审通过）。  
5. **噪音类内容**：如「楼上很吵」在打开沟通页的同时，宜走事件提案（扰民/噪音），由用户确认是否建事件；首期至少保证切房+沟通可见。  
6. **切房触发（已确认：房号 + 业务词）**：  
   - **必须同时满足**：① 解析出可匹配房号（含单元若需要）；② 同句或紧邻短窗口内出现业务信号。  
   - **业务词/业务意图**至少覆盖：收费族（欠费/预存/收到/交了…）、报修/故障族（漏水/维修/工程…）、扰民/投诉族（吵/噪音…）、原声记录信号（业主说/备注…）等与听记业务一致的类别。  
   - **仅房号**（如「看下 602」「到 201」）→ **不自动跳转**。  
   - 有业务词但房号歧义 → 先选房再跳，不默认跳第一套。  
7. **跳转时机（已确认：立刻跳）**：房号+业务词且唯一匹配时，**立即**打开沟通记录页，不插入确认弹窗或可撤销提示条；歧义匹配仍须先选房。  

### 6.5 验收要点

- 口述「一单元 201，现在楼上很吵」且本楼存在对应房：**立刻**进入该房沟通记录页（无额外确认步骤），可见历史沟通列表。  
- 口述「我们看下 602」（无业务词）：**不**自动打开沟通页。  
- 断网下跳转与列表加载正常。  
- 歧义房号不会跳错房。  
- 已在目标沟通页时重复提及同一房不造成页面反复重建闪烁。

## 7. 需求五：定时提醒（完全离线）

### 7.1 需求概述

对本机「待跟进收费」与「未完成事件」等事项，支持设置提醒时间；到点后通过**系统本地通知**提醒管家，**不依赖网络与云推送**。

### 7.2 用户场景

| 场景 | 说明 |
|------|------|
| 事件提醒 | 为「602 漏水」设「明天下午 3 点」提醒跟进工程 |
| 收费跟进 | 为「601 欠费」设「本周五」提醒催缴 |
| 听记后快捷设提醒 | 确认写入收费/事件的卡片上可「顺便设提醒」 |

### 7.3 功能需求

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F-REM-01 | 支持为**事件**设置/修改/取消提醒时间 | P0 |
| F-REM-02 | 支持为**房屋缴费跟进**（如标记待催缴）设置提醒；或创建「跟进事项」绑定房间 | P0 |
| F-REM-03 | 到点弹出本地通知（标题/正文含房号与摘要）；点击进入对应房间或事件详情 | P0 |
| F-REM-04 | 提醒数据存 SQLite；调度使用 Android 本机 AlarmManager / WorkManager 等**本地机制** | P0 |
| F-REM-05 | App 进程被杀或重启后，仍能根据本机数据恢复未触发提醒（在系统允许范围内） | P0 |
| F-REM-06 | 提醒列表：即将到来 / 已过期未处理 | P1 |
| F-REM-07 | 重复提醒（每天/每周） | P2 |
| F-REM-08 | **禁止**依赖 FCM/厂商云推送或任何联网拉取 | P0 |

### 7.4 业务规则

1. 时区与时间以设备本地时间为准。  
2. 事件标记「已完成/已取消」时可提示是否取消关联提醒。  
3. 通知权限被拒绝时，功能可用但需引导至系统设置开启（仍离线）。  
4. 精确闹钟受系统省电策略影响时，应在说明中告知「可能有延迟」，并尽量申请精确闹钟权限（Android 12+）。

### 7.5 验收要点

- 断网、飞行模式下到点仍能本地通知。  
- 重启手机后（在权限与系统限制内）未到期提醒仍有效。  
- 提醒内容可追溯到具体房间/事件。

## 9. 技术约束（需求级）

1. **ASR**：优先本机轻量中文方案（如 sherpa-onnx + Zipformer 小模型等），模型随安装包或本地只读资源提供。  
2. **语义**：首期允许「规则语义框架 + 同义族 + 会话状态」；可后续增加本机 Tiny 分类/槽位模型，仍须离线。  
3. **禁止**：云端 ASR、云端 LLM、在线词典更新、云推送提醒。  
4. **数据**：全部写入现有/扩展的本机 SQLite；备份体系可后续纳入事件与提醒字段（另文）。  
5. **导航**：仅使用本机房间索引与现有沟通记录页路由，不访问网络地图或云端房源。
