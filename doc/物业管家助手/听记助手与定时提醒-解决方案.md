## 1. 方案目标

在现有本机 App 上增量实现：

1. 楼栋网格内**离线听记**（收费写入提案、事件写入提案）  
2. **房号+业务词 → 立刻打开该房沟通记录**  
3. **本机定时提醒**（事件/收费跟进）  
4. **特征标签听记**：内置/自定义标签从会话中匹配，提案挂到房间（确认后写入）；自定义标签支持 **`description` 描述性介绍**，名称难命中时靠描述做语义精准匹配  

不引入联网 ASR/LLM/云推送；首期语义以**规则框架 + 同义族 + 会话状态**为主，ASR 用本机轻量模型；标签匹配以**本机标签库（名称 + 描述 + 可选别名）动态词表**为核心。

## 2. 总体架构

```
BuildingGridScreen（进入开听 / 离开停听）
        │
        ▼
┌───────────────────┐
│ ListenSession     │  生命周期、当前楼栋/当前房上下文、防抖
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐     ┌─────────────────────┐
│ OfflineAsrEngine  │────▶│ SemanticParser      │
│ (sherpa-onnx)     │     │ 房号/业务词/疑问/极性 │
└───────────────────┘     └──────────┬──────────┘
                                     │
                    ┌────────────────┼────────────────┐
                    ▼                ▼                ▼
            NavigateAction    PaymentProposal   EventProposal
            (立刻切沟通页)      (确认卡片)         (确认卡片)
                    │                │                │
                    ▼                ▼                ▼
         Routes.roomCommunication  UpdateRoomUseCase  EventRepository
                                     │
                                     ▼
                              ReminderScheduler（本机通知）
```

**原则：**

- 听记管道与业务写入解耦：解析只出「动作/提案」，写入走现有/新增 UseCase。  
- 切房是导航动作，不等于已记账。  
- 无关文本在 SemanticParser 直接丢弃，不进 UI。

## 5. 语音与语义方案（离线）

### 5.1 ASR

| 项 | 选型 |
|----|------|
| 运行时 | **sherpa-onnx**（Android AAR / JNI） |
| 模型 | Streaming **Zipformer-zh-14M int8**（约 25MB）内置 assets |
| VAD | Silero 或 sherpa 自带 VAD，闲时少算 |
| 生命周期 | 仅 `BuildingGrid` 在前台组合内 Start/Stop |

**改动点：** `app/build.gradle.kts` 增加 sherpa-onnx 依赖与 abiFilters（建议先 `arm64-v8a`）；`AndroidManifest` 已有 `RECORD_AUDIO`，补充前台服务（若系统要求持续麦）与通知渠道文案。

### 5.2 语义：两级流水线（规则粗筛 + 端侧小模型复核）

**结论：** 仅靠语义词表/规则**一定会漏、也会误触发**；复杂一点的会话（转述、反问、否定、指代）规则更吃力。  
因此方案采用 **两级解析**，而不是一上来上端侧大模型：

```
ASR 文本
  │
  ├─① 规则粗筛（快、零模型内存）
  │     无房号/无业务信号 → Ignore（不进 UI）
  │     有候选 → 打出「草稿动作」+ 槽位假设
  │
  └─② 端侧小模型复核（仅对候选句，省电省内存）
        输出：意图类别 + 置信度 +（可选）是否应弹出提案
        低置信 / 判为无关 → 丢弃或降级为「仅记原声选项」
        高置信 → 再出确认卡片 / 立刻切房
        中置信 → 确认卡片文案标明「请核对」（防误会）
```

用户确认卡片仍保留：**小模型防误会，不替代人工确认写入**。

#### 5.2.1 第一级：规则粗筛（M1 必做）

实现 `RuleSemanticParser.parse(...) → CandidateAction?`：

| 动作类型 | 触发 | 结果 |
|----------|------|------|
| `NavigateToRoom` | **房号 + 业务词**，唯一匹配 | 候选切房（经小模型复核后立刻跳） |
| `ProposePayment` | 收费框架 | 候选提案 |
| `ProposeEvent` | 报修/噪音等框架 | 候选提案 |
| `ProposeFeatureTags` | 命中内置/自定义标签的 **名称 / 描述关键词 / 别名** | 候选挂签（确认后写入房间特征） |
| `PendingVerify` | 疑问/传闻 | 短时状态，等「收到了/没收到」 |
| `Ignore` | 无业务信号 | 无 UI |

业务词表（`res/raw/listen_lexicon.json` 或 Kotlin object）：收费族 / 报修族 / 扰民族 / 疑问传闻 / 极性词。  
**特征标签词表**：运行时从 `FeatureTagRepository` 加载本机全部标签的 **name + description（+ 可选 aliases）**，动态并入粗筛词典（见 §5.4）。  
房号解析：`一单元/1单元` + `201/602`；与本楼 `Room` 匹配。

#### 5.2.2 第二级：端侧小模型复核（建议纳入正式方案，见触发时机）

**模型定位（不是 LLM）：** 中文 **Tiny 分类 / 轻量意图模型**（ONNX INT8），对「规则筛出的候选句」做简单语义判别。

| 推荐输出头（可多任务共享编码器） | 作用 |
|----------------------------------|------|
| `intent`：payment / event / feature_tag / navigate_context / chitchat / unclear | 防止「提到钱但不是收费」「提到吵但在开玩笑」误提案 |
| `speech_act`：assert / question / hearsay / answer_yes / answer_no | 服务「吗？/没收到」类会话 |
| `should_act`：true/false | 总闸：是否值得弹确认或切房 |
| （可选）`tag_ids` 多标签头或「句向量×(标签名+描述)相似度」 | 在候选标签集合上精排；**描述为空时仅比名称** |

| 项 | 建议 |
|----|------|
| 底座 | `uer/roberta-tiny-wwm-chinese` 或同等更小中文 RoBERTa（当前落地：`uer/chinese_roberta_L-2_H-128`），微调后导出 ONNX INT8 |
| 体积 | 目标 **约 1–5MB**（当前 `listen_intent.onnx` INT8 ≈ 3.3MB + vocab；远小于 SenseVoice/端侧 LLM） |
| 调用时机 | **仅规则命中候选时**推理；闲聊句不跑模型 |
| 运行时 | ONNX Runtime Mobile（与 ASR 错峰：ASR 出字后再跑 NLU） |
| 训练数据 | 自建 500–2000 条物业口述标注（含易混负例） |

**小模型不负责：** 开放闲聊、自由生成回复、替代确认卡片。

#### 5.2.3 什么时候必须加小模型？

| 时机 | 说明 |
|------|------|
| **建议：M1 规则基线测完后立刻规划，M3–M4 前接入复核** | 用 100～200 条真实/模拟口述量：规则漏检率、误触发率；若误提案或漏检不可接受，**必须上第二级** |
| **定量门槛（建议写入验收）** | 无关句误弹出确认 **>5%**，或业务句漏检 **>20%**，或「疑问/否定」类错误写入风险仍高 → **上小模型复核** |
| **可提前并行** | 规则上线同时收集难例；小模型数据与训练和 M2/M3 并行，避免拖到用户抱怨再补 |
| **不必等「很复杂会话」才加** | 「防误会」本身就是小模型的主价值；复杂多轮仍靠会话状态 + 确认，不靠把模型做大 |

#### 5.2.4 与「确认卡片」的分工

| 层级 | 防什么 |
|------|--------|
| 规则 | 挡住明显无关句，控制算力 |
| 小模型 | 挡住「长得像业务、语义不是」的误会；给置信度 |
| 确认卡片 | 挡住最终写库错误（金额换算、改缴费、建事件） |
| 立刻切房 | 仍要求房号+业务词；小模型 `should_act`/`intent` 不通过则**不跳**（比误跳更安全） |

### 5.3 会话状态

`ListenSessionState` 持有：

- `buildingId`、`focusedRoomId`  
- `pendingVerification`（超时 15–30s）  
- `lastNavigatedRoomId` + 冷却时间戳（防抖 8–15s）  
- `activeTagLexicon`：当前本机标签 **name / description 关键词 / aliases** 快照（标签增删改后刷新）  

### 5.4 特征标签（内置 + 自定义）听记匹配

#### 5.4.1 「含义」能识别到什么程度？

自定义标签的「含义」= **`name`（短名）+ `description`（描述性介绍，可空）+ 可选 `aliases`**，不是独立百科知识。  
**当短名难以被口语直接命中时，以描述为主做语义精准匹配**（需求 F-TAG-02/03）。

| 能力 | 可行性 | 做法 |
|------|--------|------|
| 会话里说出与标签名相同/高度相近的词 | **高** | 动态词表精确/包含匹配 |
| 名称难说、但描述写清口语场景 | **高（首期主路径）** | 描述分词/关键词 +（可选）句向量×描述相似度 |
| 内置标签（老人、小孩、宠物、在售、车辆）近义 | **高** | 预置同义族（狗→宠物、卖房→在售） |
| 无描述、无别名时的任意隐喻 | **低（不承诺）** | 仅靠名称；产品引导填写描述 |
| 一次会话挂多个标签 | **高** | 「有老人也有宠物」→ 多标签提案 |
| 去掉标签（「没宠物了」） | **中** | 极性+标签名/描述命中；确认卡片选「移除」 |

**结论：** 精准匹配依赖用户在定义标签时给出可说的线索——**名称宜短；说不清就写描述**。不承诺在描述为空时理解任意自定义隐喻。

#### 5.4.2 匹配流水线（与收费/事件共用两级）

```
本机 FeatureTag 列表（含自定义）
        │ 启动听记 / 标签变更时
        ▼
动态词典：name + description（关键词/整句）+ aliases +（内置）同义族
        │
ASR 文本 ─① 规则：房号上下文 + 标签命中 → ProposeFeatureTags 候选
        │
        └─② 小模型复核：intent=feature_tag 且 should_act
              可选：句向量与「未精确命中的标签」的 (name∥description) 算相似度，过阈值则进入候选
        │
        ▼
确认卡片：展示将「添加/移除」的标签列表（可显示描述摘要） → 确认后 UpdateRoomUseCase(featureTagIds)
```

**精准匹配优先级：**

1. **精确**：ASR 子串 == 标签 `name`  
2. **规范化**：去空格、全半角、数字中文（「一」/「1」）后再比  
3. **别名表**（P1）：短词别名精确/包含  
4. **描述匹配（P0）**：从 `description` 抽取关键词/关键短语与 ASR 做包含/重叠；或整句相似度  
5. **内置同义族**：仅对内置标签  
6. **近义召回（小模型/向量）**：对「名称未命中、描述弱命中」的补充；须更高阈值 + 确认卡片，防误挂  

**描述为空**：跳过第 4 步，仅靠名称/别名/内置同义（与现网行为兼容）。

**必须有房或当前房上下文**：与收费类似——有房号则挂该房；「这户」用 focusedRoom；否则选房或不挂签。

#### 5.4.3 数据与代码改动（标签相关）

| 项 | 说明 |
|----|------|
| 复用 | `FeatureTag` / `FeatureTagRepository` / `UpdateRoomUseCase(..., featureTagIds)` |
| **P0 必改** | `feature_tags.description TEXT NULL`；Entity/Domain/DAO/设置页创建编辑表单 |
| P1 可选 | 标签别名：`FeatureTag.aliases` 或表 `feature_tag_aliases(tag_id, alias)` |
| 新建 | `TagLexiconBuilder`：从仓库生成听记词典（含描述关键词）；`ProposeFeatureTags` 动作与确认 UI |
| 设置页文案 | 「名称尽量短；若口语说法与名称不一致，请填写描述性介绍，便于语音识别」 |
| 内置同义 | `BuiltinFeatureTagSynonyms`（宠物←狗/猫…） |

#### 5.4.4 验收示例

| 口述 | 期望 |
|------|------|
| 「602 有宠物」 | 提案：602 添加「宠物」 |
| 「这户是个老人」 | 当前房添加「老人」 |
| 名「保姆住」，描述「家里请了住家保姆或护工长期居住」；口述「请了个保姆住这儿」 | **凭描述语义命中**「保姆住」并提案（确认后写入） |
| 名「保姆住」、**描述为空**；同上口述 | 可能漏检或仅弱近义；**不降级硬编码**，引导用户补描述 |
| 「说有车但其实没有」 | 小模型/极性后不误加或提案「移除车辆」供确认 |
| 仅闲聊「我养宠物」无房上下文 | 不自动挂到错误房间 |

## 9. 分阶段实施（建议）

| 阶段 | 交付 | 验证 |
|------|------|------|
| **M1 语义可测** | RuleSemanticParser + 动态标签词典（**含 description**）+ 文本用例（无麦）；建立误触发/漏检基线 | 「602欠费」「漏水」「201很吵」「有宠物」；「保姆住+描述 vs 口述保姆」；「只说602不跳」「吗+没收到」；统计误提案率 |
| **M2 事件+提醒数据** | 表、CRUD、本地通知；同步收集小模型标注难例 | 断网到点提醒 |
| **M3 网格听记壳** | 开停听、状态条、提案卡片接 UpdateRoom/CreateEvent | 手动输入文本模拟 ASR |
| **M3.5 端侧小模型复核（建议必做）** | Tiny ONNX 意图/言语行为/should_act；仅复核规则候选 | 易混句：玩笑提「钱」、反问、否定；误提案率下降 |
| **M4 切房导航** | 房号+业务词 + 小模型通过后立刻打开沟通页 | 真机网格内口述；无业务词不跳 |
| **M5 接入 ASR** | sherpa 内置模型 | 飞行模式全程 |
| **M6 合规与打磨** | 隐私文案、权限、防抖、静音 | 过审材料 |

每阶段可独立合并，降低一次大改风险。

## 10. 风险与对策

| 风险 | 对策 |
|------|------|
| ASR 包体增大 | 仅 arm64 + 14M 小模型；文档说明安装包增量 |
| 误切房 | 强制业务词；防抖；歧义先选 |
| 误改缴费 | 一律确认卡片；金额不静默换算 |
| 自定义标签名难命中 | **定义时填写 description**；词典含描述关键词；设置页引导文案 |
| 描述过宽导致误挂 | 描述命中阈值更高 + 确认卡片；不静默写库 |
| 省电杀进程丢提醒 | Boot 重注册 + 精确闹钟权限说明 |
| 持续麦审核 | 仅网格页；状态可见；隐私政策写清 |
